# Booting your own OS on the SP-1200

You are right that your 1987 SP-1200 boots from floppy, and that fact makes your project far more feasible than it first sounds. E-mu's own service manual says that "the instructions that boot the machine are contained in EPROM. The main operating instructions are loaded into RAM from the floppy disk on power up" ([Service Manual p.39](https://archive.org/details/emu-sp-1200-service-manual-1987)). The only ROM in the machine is an **8 KB 2764 "Mainboot" loader**. The real OS (the last E-mu version was **v1.2**) sits on the first few tracks of every disk formatted with "Copy Software". The 1990s black reissues work the same way. The 2021 Rossum reissue is the exception: it stores its firmware internally and updates it from an SD card. The machine you would be targeting is a **Z-80A at 3.3 MHz with 64 KB of DRAM**, a Z-80 CTC and SIO/2, a 16×2 LCD, and a non-programmable TTL "microcontroller" that plays 8 voices out of 10 seconds of 12-bit sample memory. At least one person has already done this. **SPf1200**, by the Instagram user pfer, is a working custom OS for original units that loads from floppy like the factory one. Nobody has published source code, a disassembly, or a MAME emulator for the machine. So your practical path is: archive your disks, get an HxC SD floppy emulator, decode the OS image format, and start with a minimal "hello world" OS. Write it clean-room, or distribute it as a patch recipe, so you never redistribute E-mu's code.

## An 8 KB loader EPROM fetches the whole OS from disk

The belief that "the SP-1200 runs from ROM" comes from its predecessor. The **SP-12** (1985) keeps its OS in EPROM, and its upgrades from v2.4 to v2.6 meant swapping two OS chips ([Gearspace](https://gearspace.com/threads/emu-sp12-operating-system.659017/)). The SP-1200 dropped that design. The service manual describes "8K bytes of EPROM memory and 64K of dynamic RAM" ([Service Manual p.43](https://archive.org/details/emu-sp-1200-service-manual-1987)). A dump of that boot EPROM is in the community repo Lytrix/EMU-SP1200 as `ip362b-emu-2588.bin`. It contains the strings "SP-1200 REV B", "Loading Software", "Insert Diskette" and "Disk Read Error", which is all a pure loader needs ([Lytrix/EMU-SP1200](https://github.com/Lytrix/EMU-SP1200)). Lytrix sums it up: "Unlike the SP-12, the SP-1200 loads its OS from a floppy disk into RAM and does not use system ROMs."

The disk side is just as clear. Formatting a disk asks "copy software? Y/N", and only disks that answered yes will boot. A disk without the OS "begins to load and simply stops" ([HxC forum](https://hxc2001.com/floppy/forum/viewtopic.php?p=22343)). With no disk inserted, the unit sits in "a perpetual state of a Loading disk state" ([Gearspace](https://gearspace.com/board/rap-hip-hop-engineering-and-production/950557-sp1200-help.html)). Forum posters place the OS in "the first 5 or 6 tracks of all SP disks" and note that the machine is "ALWAYS loading the whole 'disk' at startup" ([HxC forum](https://hxc2001.com/floppy/forum/viewtopic.php?p=9811)). Holding Setup at power-on runs built-in diagnostics instead ([Tapatalk sp1200 forum](https://www.tapatalk.com/groups/sp1200/black-sp-1200-does-not-boot-on-the-software-t1828.html)).

| Version | Where the OS lives | How it boots / updates | Notes |
|---|---|---|---|
| 1987 original (grey) | Floppy (first ~5–6 tracks of any "Copy Software" disk); 8 KB boot EPROM only | Boot EPROM loads OS from 3.5" DS/DD disk into 64 KB DRAM | Final E-mu OS v1.2 ([MatrixSynth](https://www.matrixsynth.com/2011/05/e-mu-sp1200-boot-disk-v12-latest-os.html)); HD disks reportedly unreliable |
| 1990s black reissues (1993, 1998) | Floppy, same scheme | Same; a black-unit Gotek user had to name the OS image DSKA0000.HFE before it would boot ([HxC forum](https://hxc2001.com/floppy/forum/viewtopic.php?t=1750&start=15)) | HD disks reportedly work on black units; a 1998 unit is sold as having a "native HD/DD" drive ([Reverb](https://reverb.com/item/96833070-e-mu-sp-1200-1998-reissue-7030-rare-native-hd-dd-floppy-drive-best-sp1200-on-the-market)) |
| 2020 35th Anniversary "Renovation" | Rebuilt originals with an SD floppy emulator integrated into the original software ([Gearnews](https://www.gearnews.com/?p=111986)) | Disk-image based | No longer available |
| Rossum reissue (2021–2025) | Internal firmware, "same Z-80 processor and memory map as the original" | `sp1200fw.bin` on SD root, Setup → 23 → 28, power cycle; Main FW 1.04 (May 2024) is current ([Rossum documentation](https://shop.rossum-electro.com/pages/documentation)) | 20 s sample memory; production ended after the 100-unit 40th Anniversary Edition ([Bonedo](https://www.bonedo.de/artikel/namm-2020-rossum-electro-music-legt-die-sp-1200-neu-auf/)) |

Rossum also quietly confirms the disk-boot design. Every reissue ships with a 3.5" floppy of "modified software for original vintage SP-1200 units" that adds MIDI transfer of sounds and sequences ([MusicTech](https://musictech.com/news/e-mu-sp-1200-reissue-dave-rossum-electro-music-sp1200)). That disk is an official modified OS for machines like yours, and it needed no hardware change at all.

Some details remain unconfirmed. No E-mu changelog for versions before v1.2 surfaced. It is also unknown whether the 1993 and 1998 runs changed the boot EPROM revision.

## A Z-80, a 1.2 ms tick, and a sound engine you configure but cannot program

The architecture is compact, and the service manual documents it well. The full 106-page manual, with theory of operation, signal names, an 18-sheet schematic and a parts list, is scanned on the Internet Archive ([archive.org](https://archive.org/details/emu-sp-1200-service-manual-1987)). E-mu describes the SP-1200 as "very much like the Drumulator and the SP-12": a Z-80 host plus "a custom designed micro-controller" for multiplexed audio ([Service Manual p.39](https://archive.org/details/emu-sp-1200-service-manual-1987)).

**CPU and memory.** The CPU is a Z-80A at 3.3 MHz (20 MHz crystal ÷ 6). The 64 KB of DRAM program memory, made from two 4464 chips, holds "the program variables, CPU stack and sequencer memory" as well as the OS ([Service Manual pp.39, 43](https://archive.org/details/emu-sp-1200-service-manual-1987)). That one fact sets your biggest constraint: your code, your variables and every user sequence share 64 KB. SPf1200 had to delete Write SMPTE, MIDI sample dump, Name Sound, Format Disk and more to make room for new features ([SPf1200.com](https://spf1200.com/)). For scale, the Rossum OS binary is 24,912 bytes ([Lytrix/EMU-SP1200](https://github.com/Lytrix/EMU-SP1200)).

The research team disassembled the boot ROM, and its startup sequence suggests a "shadow ROM" scheme. At reset it sets `SP` to 6200h, initialises the LCD, runs a lamp test, fills all 64 KB with FFh and selects interrupt mode 2. After a successful load it jumps to 0002h, which executes `OUT (58h),A` and falls through to 0004h. The Rossum image begins with four NOPs and then `JP 0079h` at 0004h. So the OS is most likely loaded at 0000h, port 58h switches the EPROM out, and execution enters at 0004h. This is inference from code. It has not yet been confirmed against schematic sheet 3 or the undumped IC130 PAL.

**Sound engine.** Sound memory is 256K × 12-bit words in four 2.5-second banks that "sounds cannot cross over into" ([Service Manual p.41](https://archive.org/details/emu-sp-1200-service-manual-1987)). The Z-80 never streams audio. "The CPU tells it where the sound is, the length, pitch, and loop points if any, then the µC generates all the signals." The CPU reaches that microcontroller through **five I/O ports**: the input register, the register-file address latch, the level register, the bank select and the request latch ([Service Manual p.51](https://archive.org/details/emu-sp-1200-service-manual-1987)). Pitch comes from adding a 7-bit increment that either repeats or skips samples; the 7541 DAC never changes rate. The CPU "only sends values … which create semitone tuning intervals" ([Service Manual p.53](https://archive.org/details/emu-sp-1200-service-manual-1987)). Sampling reuses the 12-bit DAC as a successive-approximation ADC while "the CPU is in a wait state" ([Service Manual pp.48–51](https://archive.org/details/emu-sp-1200-service-manual-1987)). The decay and SSM2044 filter envelopes on the two dynamic-filter channels appear to be generated by the CPU ([Tapatalk sp1200 forum](https://www.tapatalk.com/groups/sp1200/adjusting-the-1200-s-filters-t561.html)). That is good news: it means you control the envelope behaviour in software.

**Peripherals.** The CTC fires "an interrupt … every 1.2 milliseconds" to scan buttons and sliders. Two of its channels are cascaded for "very high resolution (.1 BPM) sequencer timing" ([Service Manual p.43](https://archive.org/details/emu-sp-1200-service-manual-1987)). The SIO/2 "sends and receives all the signals for MIDI, SMPTE, Sync and the disk drive." **There is no floppy controller chip.** The drive runs from SIO pins plus a one-shot sync separator, switched against SMPTE by a 74LS157, and "no other SP1200 functions are accessible during disk operations" ([Service Manual pp.43–44](https://archive.org/details/emu-sp-1200-service-manual-1987)). That explains why the disk format is "100% incompatible with the PC world" and shared with the Emulator II ([HxC forum](https://hxc2001.com/floppy/forum/viewtopic.php?p=10255)). The LCD sits directly on the data bus as an I/O port. LEDs are a write-only latch where 0 means on. The sliders and the piezo velocity pad go through an ADC0809 ([Service Manual pp.43–45, 86](https://archive.org/details/emu-sp-1200-service-manual-1987)).

The research team derived the following tentative port map from the boot ROM and checked it against the sheet-4 decoders. Treat it as a starting hypothesis to verify, not as documentation.

| Port | Function (inferred) |
|---|---|
| 40h–41h | Sound memory data (byte/nibble halves) |
| 48h–4Bh | CTC channels 0–3 |
| 50h–53h | SIO/2: A = MIDI (×64 clock → 31,250 baud), B = SMPTE/cassette/disk read |
| 58h | Read: button columns; Write: likely boot-ROM disable |
| 60h–63h | Used by Rossum OS only; possibly bank select or request latch |
| 80h–87h | µC sound level lo/hi |
| 88h | Button row select |
| 8Ch / 90h | LED latches (0 = on) |
| 94h | µC register-file address latch |
| 98h / 9Ch | µC input register lo / hi |
| A0h / A1h / A2h | LCD instruction / data / status (HD44780-style init 38h, 0Ch, 01h) |
| C0h | ADC0809 select-and-start / read |

The real unknowns are the register-file layout inside the microcontroller (which addresses hold start, length, pitch and loop for each channel), the contents of the IC67 microcode PROM (not dumped), the RAM memory map, and the exact on-disk encoding. You can recover all four by disassembly, but none is written down anywhere public.

## One working custom OS, one reissue patcher, and a small scattered community

**SPf1200** is the project to study. It describes itself as "an unofficial, custom operating system for the E-mu SP-1200," "loaded off the floppy like the factory one." The current version is v1.110, and it supports original units only. Putting the factory disk back restores the stock machine ([SPf1200.com](https://spf1200.com/)). Its feature list shows what users want from a new OS: input monitoring while sampling, chopping across pads while recording, auto-truncation, a two-line display, mute/solo, undo/redo of takes, a count-in, 16th-note swing, beat repeat, and MIDI from banks E–H. The removed features show that it reworks the factory code rather than replacing it. pfer does not distribute OS images, publishes no source or license, and is reachable only through Instagram (instagram.com/pfer). Producers such as Cookin Soul and Lewis Parker are credited with feature requests.

**mod_pr4x1s** is the second project. It ports a subset of SPf1200's features to the Rossum reissue's firmware 1.04 ([sp1200.pr4x1s.fm](https://sp1200.pr4x1s.fm/)). Its distribution model is worth copying. Your browser checks your own unmodified Rossum download, applies byte patches locally from a `recipe.js`, and writes out a file that runs from RAM until power-off. The repo warns users not to share the output because it contains Rossum's firmware ([GitHub SP-1200/mod_pr4x1s](https://github.com/SP-1200/mod_pr4x1s)). It is the only SP-1200 patch code anyone can inspect. It does not run on original units, because the two machines boot differently.

Beyond these two, the record is thin. A dxarmy forum thread, "Hacking the SP's Operating System… Is it possible and who's up for the challenge?", dates from around 2017–2018. It proposed extracting the OS from HxC images and disassembling it, and it never reached a published result ([Tapatalk](https://www.tapatalk.com/groups/sp1200/hacking-the-sp-s-operating-system-is-it-possible-a-t1949.html)). MAME has no SP-1200 or SP-12 driver; `src/mame/emusys/` contains only Emax, Emulator II, Emulator III and the 68k systems ([mamedev/mame](https://github.com/mamedev/mame/tree/master/src/mame/emusys)). GitHub search found no SP-1200 disassembly. "SP-1200" plugins such as Inphonik RX1200 model the sound, not the firmware ([Synth Anatomy](https://synthanatomy.com/2023/05/inphonik-rx1200-sampler-plugin-emulates-the-legendary-12-bit-e-mu-sp-1200.html)).

The community gathers in a few places:

- **dxarmy SP-1200 forum on Tapatalk.** This is where older technical lore lives: the OS-hacking thread, SP-12 EPROM images, floppy emulator threads ([Tapatalk](https://www.tapatalk.com/groups/sp1200/sp-12-os-upgrade-t1187.html)).
- **HxC2001 forum, E-mu SP1200 section.** Admin Jeff Del Nero answers questions there and points users to the OS images in the HxC QuickInstall archive ([HxC forum](https://hxc2001.com/floppy/forum/viewtopic.php?t=4120)).
- **Gearspace, ModWiggler and MPC Forums,** for general threads.
- **Instagram,** for pfer's circle.
- **Lytrix/EMU-SP1200 on GitHub.** This is the most useful single hardware resource: a KiCad redraw, BOM, PROM/PAL dumps, the boot EPROM, and HFE images including `SP1200_OS12.hfe`. It was still active as of 2026 ([Lytrix/EMU-SP1200](https://github.com/Lytrix/EMU-SP1200)).

No dedicated Reddit, Discord or Facebook group could be verified. Treat them as possible but unconfirmed.

## A five-stage path from disk image to your own firmware

**Stage 1: protect the machine and set up a fast test loop.** Image your original disks first, using Kryoflux or HxC, which is how the community archives them ([Gearspace](https://gearspace.com/board/electronic-music-instruments-and-electronic-music-production/816011-archiving-sp1200-disks.html)). Then install a floppy emulator. A **classic Lotharek HxC SD** is the safer choice. Gotek units running HxC firmware load reliably but have corrupted images on write and failed at formatting, and HxC users steer SP-1200 owners toward the Lotharek unit ([HxC forum](https://hxc2001.com/floppy/forum/viewtopic.php?t=1750)). Writes do not matter much for OS testing, because you build images on a PC and only need the SP to read them. An external HxC wired through a switch lets you keep the real drive as a fallback ([HxC forum](https://hxc2001.com/floppy/forum/viewtopic.php?t=714)). Name your test image DSKA0000.HFE so it is the one that boots. Your recovery plan is always the same: power off, select the stock OS image, power on. Nothing you write can brick the unit, because the boot EPROM is never touched. No source covers FlashFloppy-specific SP-1200 support, so test it yourself before relying on it.

**Stage 2: decode the disk format.** This is the gating problem. No source documents the track and sector layout, so recover it from the boot ROM's disk-read loop (SIO ports 52h/53h). Disassemble the loader with Ghidra or a Python Z-80 disassembler such as `z80dis`, which the research team used, and cross-check against the floppy signals on schematic sheets 2 and 4. Then write a small tool that reads the raw bitstream from an HFE file (`SP1200_OS12.hfe`), extracts the OS binary, and writes your own binary back into a valid image. The "SP1200/EII format" remark means Emulator II disk knowledge may help here.

**Stage 3: build a test harness.** Writing an SP-1200 driver for MAME is optional, but it would save you hundreds of power cycles. MAME already has the device models you need: z80, z80ctc, z80sio, adc0808 and hd44780 are all used by its Emulator II skeleton ([MAME emu2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/emusys/emu2.cpp)). A driver needs the boot EPROM, the port map above, a front-panel layout and a register-level model of the voice microcontroller. It would also be the first SP-1200 emulator anywhere, which makes it a strong contribution in its own right.

**Stage 4: get to "hello world," then make sound.** Assemble with a standard Z-80 assembler such as sjasmplus or z80asm. Target load address 0000h with entry at 0004h, set up an IM 2 vector table for the CTC and SIO, start the 1.2 ms tick, and print to the LCD at A0h/A1h. Next scan the button matrix and read the ADC. Last, trigger one voice through the microcontroller ports. The 1987 E-mu OS v1.2 shows you how to talk to the microcontroller, and the Rossum image is a compact second reference: it shares the boot ROM's RST 08h sound-memory routine and port set. Use both for interoperability study only. The SP-12's service manual ([vintagesynthparts.com](https://www.vintagesynthparts.com/wp-content/uploads/2016/08/EMU_SP12_Service_Manual.pdf)) and its ROMs are useful cross-references, because the voice architecture carries over.

**Stage 5: choose clean-room or patch, then decide how to distribute.** Patching v1.2 gets features into your hands fastest. pfer evidently took that route, and you inherit E-mu's sequencer, disk routines and sound loading. A clean-room OS is much more work: sampling via the SAR loop, the disk writer and SMPTE all have to be rewritten. In return you get code you own outright and 64 KB laid out the way you want. A sensible hybrid is to patch first to learn the hardware, then rewrite subsystem by subsystem.

**Legal and IP cautions.** These are general, not legal advice. E-mu's code and manuals remain copyrighted. E-mu was acquired by Creative in 1993 ([Wikipedia](https://en.wikipedia.org/wiki/E-mu_SP-1200)), and the service manual scan is watermarked "For the personal use of SP1200 Owners only" ([archive.org](https://archive.org/details/emu-sp-1200-service-manual-1987)). Every existing project avoids shipping vendor code. SPf1200 distributes no image, and mod_pr4x1s patches the user's own download and forbids sharing the output. Neither Creative nor Rossum has made any public statement on modding. So the lower-risk ways to share your work are original code written from the hardware documentation, or a patcher that changes the user's own copy of v1.2 and contains none of E-mu's bytes. Avoid publishing a modified E-mu OS image. Contacting pfer before you release anything would also avoid stepping on the one active developer.

## Conclusion

The SP-1200 is unusually friendly to firmware work for a 1987 instrument. Because the OS lives in RAM and loads from disk, every experiment is reversible, and with an HxC emulator each test costs only a power cycle. The difficulty is not the Z-80. It is the undocumented parts around it: the disk encoding, the voice microcontroller's register layout, and 64 KB shared with user data. Whoever decodes those first, and publishes the result, will matter more to the community than any single feature.

The landscape favours openness. The only working custom OS is closed and reachable only through Instagram. No emulator exists. The best hardware repository is a single hobbyist's GitHub. An SP-1200 MAME driver, an HFE pack/unpack tool, or a documented port and memory map would each fill a public gap. They would also make your own OS easier to build, and they carry none of the IP risk of shipping firmware.
